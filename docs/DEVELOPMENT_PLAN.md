## 1. 프로젝트 개요 및 추진 목표

### 1-1. 배경 및 목적
- 매일 아침 "오늘 날씨에 대체 뭘 입어야 할까?" 고민하는 시간을 줄이기 위해, **도시 선택 한 번으로 실시간 날씨 분석과 3가지 스타일별(캐주얼/출근/스포티) 부위별 맞춤 코디를 5초 이내에 제공**하는 서비스 구축.
- 단순 날씨 앱의 수치 제공을 넘어, 직관적인 **인터랙티브 캐릭터 옷장과 체감온도 표정 게이지, 날씨 연동 애니메이션 배경**을 통해 실용성과 즐거움을 동시에 전달.

### 1-2. 핵심 지표 (KPI)
1. **첫 화면 로딩 속도**: LCP(Largest Contentful Paint) 1.5초 이내 달성
2. **조작 응답성**: 도시 선택 및 스타일 탭 전환 지연시간 100ms 이내
3. **가용성**: 외부 날씨 API 장애 또는 오프라인 상태에서도 적절한 Fallback 제공 (서비스 다운타임 0%)
4. **인프라 비용**: 서버 유지비용 월 0원 유지

> 현황(2026-10-29, 로컬 프로덕션 빌드 + 헤드리스 Chrome 에뮬레이션 실측, 5-3 참고): 2번은 충족(탭 전환 중앙값 22~39ms). 1번은 무제한 환경에서 중앙값 약 1.35초로 충족하나 편차가 크고, Slow 4G + CPU 4배 감속 환경에서는 약 1.85초로 미달 — 실기기 미측정. 3번은 오류·오프라인 화면, AI 폴백, 서비스 워커 오프라인 셸로 구현·검증. 4번은 무료 티어 구성으로 충족 예정(배포 전).

## 3. 시스템 아키텍처 및 모듈 설계

### 3-1. 아키텍처 다이어그램
```
┌─────────────────────────────────────────────────────────────┐
│                       Client Browser                        │
│                                                             │
│  [TopBar] ── [WeatherStage] ── [WardrobeCard] ── [BagCard]  │
│      │               │          (+ShareButton)       │      │
│      └───────────────┼─────────────────┴─────────────┘      │
│                      ▼                                      │
│               [page.tsx Controller]                         │
│             (State & Lifecycle Manager)                     │
│                      │                                      │
│        ┌─────────────┼─────────────┬──────────────┐         │
│        ▼             ▼             ▼              ▼         │
│   [api.ts]      [rules.ts]   [share-card.ts]  [sw.js]       │
│  (Network)   (Recommendation) (Canvas PNG)  (Static cache)  │
└────┬────────────────┬──────────────────────────────────────┘
     │                │ (Internal Pure Logic)
     │                ▼
     │         ┌──────────────────┐
     │         │ 45개 도시 DB     │
     │         │ 기온·스타일 룰셋 │
     │         └──────────────────┘
     │
     ├─ (Direct Fetch, No Key) ──▶ Open-Meteo API (날씨)
     │
     └─ GET /api/comment?city=… ─▶ [Route Handler: app/api/comment/route.ts]
                                    ├─ CityId 검증 (400)
                                    ├─ KST 1시간/도시 인메모리 캐시
                                    ├─ Open-Meteo 재조회 + Gemini 호출 (서버 전용 키)
                                    └─ 실패 시 rules 기반 폴백 코멘트
```

### 3-2. 컴포넌트 계층 및 책임 분리 (Separation of Concerns)

| 계층 | 모듈/컴포넌트 | 책임 및 역할 |
|---|---|---|
| **컨트롤러** | `app/page.tsx` | 도시 상태, 날씨 데이터 페칭, AbortController 생명주기 제어, 로컬스토리지 동기화, 테마 결정 |
| **비주얼 배경** | `theme-background.tsx` | 현재 날씨 상태(비, 눈, 맑음, 안개 등)에 따른 CSS 키프레임 애니메이션 및 다크 테마 제어 |
| **헤더/입력** | `top-bar.tsx` | 권역별(`optgroup`) 45개 도시 선택 드롭다운, 새로고침(↻) 트리거 |
| **날씨 스테이지** | `weather-stage.tsx` | 현재 기온, 최고/최저, 체감온도 표정 슬라이딩 게이지(-10℃~35℃) 렌더링 |
| **추천 옷장** | `wardrobe-card.tsx` | 3가지 스타일 탭, 옷장 문 개폐 연출, 터치 반응형 캐릭터 아바타, 세부 코디 그리드, 날씨 팁 배너 |
| **가방/대시보드** | `bag-and-info.tsx` | 기상 특보 연동 소지품 스티커 틸트 렌더링, 강수/풍속/자외선 3열 미니 정보 대시보드 |
| **상태 뷰** | `state-views.tsx` | 로딩 스켈레톤, API 오류 화면, 오프라인 화면 및 재시도 액션 |
| **도메인 규칙** | `rules.ts` | 45개 도시 위경도 데이터셋, 기상 코드 매핑, 체감온도 구간별 코디 룰셋, 특보 배지 계산기 |
| **통신/유틸** | `api.ts` | Open-Meteo API 호출, 타임아웃·취소 제어, `/api/comment` 호출(AI 코멘트와 출처 반환), KST 날짜/시각 포맷팅 |
| **공용 날씨 로직** | `weather-shared.ts` | Open-Meteo 조회 URL·응답 파싱, 규칙 기반 한마디 (서버·클라이언트 공용) |
| **AI 중계** | `app/api/comment/route.ts` | 도시 ID 검증, 캐시(AI 1시간/폴백 2분)·동시 요청 병합, Gemini 호출, 규칙 기반 폴백, 날씨 실패 시 503 |
| **테스트** | `tests/*.test.ts` | 추천 엔진·날씨 파싱 단위 테스트 (`npm test`) |
| **공유** | `share-button.tsx`, `_lib/share-card.ts` | 선택 스타일 기준 1080×1350 PNG 생성, Web Share API 또는 다운로드 |
| **PWA** | `app/manifest.ts`, `public/sw.js`, `sw-register.tsx` | 매니페스트, 정적 리소스 캐시, 프로덕션 한정 서비스 워커 등록 |

## 5. 품질 보증 (QA) 및 테스트 계획

### 5-1. 단위 및 로직 테스트 케이스 [구현·통과]
`npm test`(Node 내장 테스트 러너, `tests/rules.test.ts`, `tests/weather-shared.test.ts`) — 18건 통과.

`rules.ts`의 `recommend` 엔진:
1. **체감온도 경계값** (경계값은 윗 구간, 1℃ 낮으면 아랫 구간): 28℃↑ 폭염 / 23~27 초여름 / 17~19 맨투맨·니트 / 12~16 자켓·가디건 / 5~8 숏패딩·코트 / 4℃↓ 헤비 롱패딩·장갑. −20~40℃ 전 구간 3개 스타일의 코디가 비어 있지 않음
2. **특보 및 소지품 배지** (코드의 실제 임계값 기준):
   - 강수확률 60% 이상 또는 비·뇌우·이슬비 코드: `☂️ 우산 필수`, 캐릭터 신발 부츠·손 우산
   - 강수확률 30~59%: `🌂 접이식 우산 추천`, 29% 이하·결측: 없음
   - 눈 코드: `❄️ 미끄럼 주의 신발`, 장갑·부츠
   - 풍속 30km/h 이상: `🌬️ 바람 강해요` 및 방풍 팁 (29는 없음)
   - 일교차(최고−최저) 10℃ 이상: `🧣 일교차 커요` (9℃ 차이는 없음, 결측은 없음)
   - UV 지수 6 이상: `🧴 자외선 강해요` 및 볼캡 (5는 없음)
3. **결측 처리**: 모든 측정값이 null이어도 예외 없이 추천, 체감온도가 없으면 기온으로 대체
4. **`weather-shared.ts`**: Open-Meteo 응답 파싱(체감온도 대체, 기온 전무 시 오류, 비정상 daily 처리), 조회 URL(KST·좌표), 규칙 기반 한마디(28℃↑ 💧, 4℃↓ 🔥, 결측 시 기온 팁 생략)

### 5-2. URL Mock 모드를 활용한 E2E 시나리오 점검
> 수행 이력(2026-10-29): 로컬 프로덕션 빌드를 헤드리스 Chrome(CDP)으로 모바일 에뮬레이션(390×844, 360×740, DPR 2)해 아래 5개 시나리오를 모두 확인함. 모든 화면에서 콘솔 오류 없음, 가로 스크롤 넘침 0px. 실제 Safari·Android 기기는 확인하지 못함. Claude-in-Chrome 확장이 연결되지 않아 CDP로 대체했음.

개발 서버에서 URL 파라미터를 통해 모든 상태를 즉시 재현 가능:
- `http://localhost:3000/?mock=loading`: 로딩 스켈레톤 화면 정상 동작 점검 ✔
- `http://localhost:3000/?mock=error`: 통신 오류 뷰 및 [다시 시도] 버튼 표시 ✔ (버튼 재호출 동작은 클릭으로 확인하지 않음)
- `http://localhost:3000/?mock=offline`: 오프라인 뷰 표시 ✔ (네트워크 복구 시 자동 재시도는 확인하지 않음)
- `http://localhost:3000/?weather=65&temp=15&pop=80`: 비 오는 날씨 테마 및 우산 필수 코디 시뮬레이션 ✔
- `http://localhost:3000/?weather=73&temp=-5&wind=35`: 눈 오는 혹한기 테마 및 방한화/패딩 시뮬레이션 ✔

### 5-3. 서버 장애 경로 및 성능 측정 결과
**서버 장애 경로** (`next start` 프로세스에 `fetch` 스텁을 선로딩해 외부 호출만 실패시킴):
| 시나리오 | 결과 |
|---|---|
| Open-Meteo 실패 | `/api/comment` 503 + `comment: null`, 캐시하지 않음 → 화면은 클라이언트 규칙 문구 표시 |
| Gemini HTTP 500 | 규칙 기반 폴백(`source: "fallback"`), 2분 캐시 |
| Gemini `finishReason: MAX_TOKENS` | 응답 폐기 후 폴백 |
| 같은 도시 동시 요청 5건 | Gemini 호출 1회 |
| 잘못된 도시 | 400 |
| 키 전달 방식 | `x-goog-api-key` 헤더만 사용, URL에 키 없음 |

**성능** (로컬 프로덕션 빌드, 캐시 비활성, 실제 Open-Meteo 호출 포함, 각 5회):
| 환경 | LCP | 스타일 탭 전환 |
|---|---|---|
| 에뮬레이션 없음 | 684~2248ms, 중앙값 약 1.35초 (FCP 약 0.2초) | 중앙값 22~30ms |
| Slow 4G + CPU 4x (`preconnect` 적용 후) | 1700~2816ms, 중앙값 약 1.85초 | 중앙값 39ms (최대 256ms) |
| Slow 4G + CPU 4x (`preconnect` 적용 전) | 1868~5636ms, 중앙값 약 4.5초 | 중앙값 103ms |
- LCP 요소는 AI 한마디·코디 요약 문단이며, 변동의 주원인은 외부 Open-Meteo 응답 시간(약 0.24~1.0초)
- 한계: 데스크톱 헤드리스 Chrome의 에뮬레이션이며 실기기 값이 아님. 표본이 작고 외부 API 지연에 좌우됨. 실제 Gemini 응답(미캐시 시 1~4초)을 기다리는 경로는 스텁(0.8초)으로 대체해 측정함
- 판정: 탭 전환 100ms KPI는 충족. LCP 1.5초 KPI는 일반 환경 중앙값에서 충족하나 느린 환경에서는 미달

## 6. 배포 및 운영 전략

### 6-1. 빌드 및 배포 파이프라인
1. **패키지 매니저**: `pnpm` (Corepack 연동)
2. **프로덕션 빌드**: `pnpm build` (`next build --webpack`) — pnpm이 없는 환경에서는 `npx next build --webpack`으로 동일하게 빌드 가능
   - 정적 페이지(SSG) 사전 렌더링 완료
3. **PWA 유의사항**: 서비스 워커·설치는 HTTPS(또는 localhost)에서만 동작. 서비스 워커는 프로덕션 빌드에서만 등록되며, 캐시 이름 버전(`public/sw.js`의 `VERSION`)을 올리면 이전 캐시가 정리됨.
4. **호스팅 추천 옵션**:
   - **옵션 A (권장)**: Vercel 배포 (Next.js 공식 최적화 호스팅, 엣지 캐시 무료, 0원 운영)
   - **옵션 B**: Cloudflare Pages + Workers (무료 정적 배포 + 무료 서버리스 프록시)
   - **옵션 C**: 로컬 서버 / 사내 인트라넷 데몬 구동 (`pnpm start`, 포트 3000)

### 6-2. 모니터링 및 무중단 운영 수칙
- 클라이언트 측 에러 바운더리(`ErrorView`) 구축으로 예외 발생 시 전체 앱 크래시 방지
- Open-Meteo API 호출 실패 시 직전 캐시 데이터 활용 또는 친절한 재시도 가이드 제공
- Gemini API 키 및 환경변수는 GitHub 저장소에 절대 커밋하지 않고 배포 플랫폼 환경변수(Secrets)로 주입
